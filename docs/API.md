# Lekan AI – API Reference

Everything a frontend needs to integrate with the Lekan AI backend: endpoints, request and response shapes, errors, the chat and approval flow, and TypeScript types.

- **Base URL (local):** `http://localhost:8000`
- **Format:** JSON in, JSON out (`Content-Type: application/json`), except the two browser redirect endpoints under `/auth/google`.
- **Interactive docs:** `GET /docs` (Swagger UI) and `GET /openapi.json` (OpenAPI schema), both generated by FastAPI.
- **Auth:** the API itself has **no authentication**. See [Security notes](#security-notes) before exposing it anywhere other than your own machine.

## 1. Quick start for frontend devs

The main loop of the app is three calls:

```
1. GET  /auth/status        → is Google connected? If not, send the user to /auth/google
2. POST /chat               → send a message, get a reply OR a list of actions needing approval
3. POST /chat/approve       → approve or reject those actions, get the reply (or more approvals)
```

Minimal example:

```ts
const API = "http://localhost:8000";

let threadId: string | null = null; // null = start a new conversation

async function send(message: string) {
  const res = await fetch(`${API}/chat`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ message, thread_id: threadId }),
  });
  if (!res.ok) throw await res.json();           // { detail: ... }
  const data: ChatResponse = await res.json();
  threadId = data.thread_id;                      // keep it for the next message
  return data;                                    // render data.reply OR data.pending_approvals
}
```

To start a "New chat", set `threadId = null`.

## 2. Before you start: CORS

> ⚠️ **The backend does not currently enable CORS.**
> A web app served from a different origin, such as `http://localhost:3000` or `http://localhost:5173`, will have its `fetch` calls **blocked by the browser**.

You have two options:

- **Dev proxy (no backend change):** proxy `/api/*` to `http://localhost:8000` in your dev server, e.g. Vite's `server.proxy` or Next.js `rewrites`.
- **Backend change:** add FastAPI's `CORSMiddleware`, allowing your frontend origin. Ask the backend owner.

## 3. Error format

### 3.1 Errors raised by the API (`4xx` / `502`)

FastAPI's standard shape. `detail` is a **human-readable string** that is safe to show to the user:

```json
{ "detail": "This conversation is waiting for your approval. Use POST /chat/approve first." }
```

### 3.2 Validation errors (`422`)

These come back when the request body is malformed, for example a missing `message` or a wrong type. `detail` is an **array**:

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "message"],
      "msg": "Field required",
      "input": { "thread_id": null }
    }
  ]
}
```

> Tip: handle both cases. `typeof err.detail === "string" ? err.detail : err.detail.map(d => d.msg).join(", ")`

### 3.3 Unexpected server errors (`500`)

The response body is **plain text** `Internal Server Error`, **not JSON**. Don't call `res.json()` blindly on a 500. Typical causes:

- The OpenAI API failed: bad key, quota exceeded or outage.
- Google refused to refresh the saved login, because it was revoked. This applies to the `/google/*` endpoints.
- A Google login code was rejected in `/auth/google/callback`.

### 3.4 Status code summary

| Code | Meaning | Where |
|---|---|---|
| `200` | Success | all |
| `307` | Redirect to Google | `GET /auth/google` |
| `400` | Bad request (message in `detail`) | `/auth/google/callback`, `/chat/approve` |
| `401` | Google not connected | `/google/*` |
| `409` | Conversation is waiting for approval | `POST /chat` |
| `422` | Malformed request body | `POST /chat`, `POST /chat/approve` |
| `500` | Unexpected server error (plain text) | any |
| `502` | Google API rejected the request | `/google/*` |

## 4. Health

### `GET /health`

Checks that the server is running and that Google credentials are configured on the server. It does **not** check whether the user has connected their Google account; use `/auth/status` for that.

**Response `200`**
```json
{
  "status": "ok",
  "google_configured": true
}
```

| Field | Type | Description |
|---|---|---|
| `status` | `"ok"` | Always `"ok"` when the server responds |
| `google_configured` | `boolean` | Server has a Google client ID and secret |

## 5. Google connection (OAuth)

The backend holds **one** Google account's login, for the single owner of the assistant. The frontend's job is to:

1. check whether Google is connected,
2. send the user through Google's login screen if it isn't, or if `needs_reconnect` is `true`.

### 5.1 `GET /auth/status`

Call this on app load, and after the user comes back from connecting Google.

**Response `200`** comes in **three possible shapes**. Always check `connected` first.

**a) Connected**
```json
{
  "connected": true,
  "scopes": [
    "openid",
    "https://www.googleapis.com/auth/userinfo.email",
    "https://www.googleapis.com/auth/gmail.readonly",
    "https://www.googleapis.com/auth/calendar.readonly",
    "https://www.googleapis.com/auth/calendar.events",
    "https://www.googleapis.com/auth/drive"
  ],
  "missing_scopes": [],
  "needs_reconnect": false,
  "has_refresh_token": true
}
```

**b) Never connected**
```json
{
  "connected": false,
  "reason": "Not connected yet. Visit /auth/google."
}
```

**c) Login revoked or expired** (for example, the user removed access in their Google account settings)
```json
{
  "connected": false,
  "reason": "Token revoked or expired. Visit /auth/google to reconnect."
}
```

| Field | Type | Present when | Description |
|---|---|---|---|
| `connected` | `boolean` | always | `true` = Google calls will work |
| `reason` | `string` | `connected: false` (cases b, c) | Human-readable explanation |
| `scopes` | `string[]` | case a | Permissions the saved login has |
| `missing_scopes` | `string[]` | case a | Permissions the backend needs but the login lacks |
| `needs_reconnect` | `boolean` | case a | `true` → send the user through `/auth/google` again. Happens when the backend adds a new feature that needs more permission |
| `has_refresh_token` | `boolean` | case a | `false` means the login will stop working within about 1 hour. Reconnect |

> Note: in rare cases (a), `connected` can be `false` while `scopes` is present, meaning a saved login exists but is unusable. Treat any `connected: false` as "show the Connect Google button".

**Suggested UI logic**
```ts
const s = await (await fetch(`${API}/auth/status`)).json();
if (!s.connected || s.needs_reconnect || s.has_refresh_token === false) {
  showConnectGoogleButton(s.reason ?? "Google needs to be reconnected to enable new features.");
}
```

### 5.2 `GET /auth/google`

Starts the Google login. **This is a browser navigation, not a `fetch`.**

```ts
window.location.href = `${API}/auth/google`;
// or open in a new tab / popup:
window.open(`${API}/auth/google`, "_blank");
```

**Response:** `307 Temporary Redirect` to `accounts.google.com`.

> Don't call this with `fetch`. It redirects to Google's login page, which must be shown in the browser.

### 5.3 `GET /auth/google/callback`

**Google calls this, not the frontend.** It's documented so you know what the user sees at the end of the login.

The user lands on this URL in their browser, and it returns **JSON**, not a page or a redirect back to your app:

**Response `200`**
```json
{
  "message": "Google account connected. You can close this tab.",
  "has_refresh_token": true
}
```

**Errors `400`**

| `detail` | Cause |
|---|---|
| `"Google returned an error: access_denied"` | User clicked Cancel on Google's screen |
| `"Missing code or state from Google."` | URL opened manually or malformed |
| `"Unknown or expired login attempt. Start again at /auth/google."` | Login link reused, or the server restarted mid-login |

**Recommended frontend pattern** (given that the callback doesn't redirect back to your app):
1. Open `/auth/google` in a **new tab or popup**.
2. Show "Waiting for Google…" in your app, with a **"I've connected – check again"** button. You can also poll `GET /auth/status` every 2–3 seconds until `connected` is `true`.
3. Tell the user they can close the Google tab when it says "connected".

## 6. Chat

### 6.1 `POST /chat`

Sends one user message to the assistant.

**Request body**

```json
{
  "message": "What's on my calendar tomorrow?",
  "thread_id": null
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `message` | `string` | ✅ | The user's message |
| `thread_id` | `string \| null` | ❌ | Conversation ID. **Omit or `null` to start a new conversation.** Send the `thread_id` from the previous response to continue it |

**Response `200`**: `ChatResponse`. It is **one of two kinds**:

**a) A normal reply**
```json
{
  "thread_id": "f79cdb0c-72fb-49c4-acbc-ad818bb8eb40",
  "reply": "Tomorrow you have:\n- 10:00 Standup\n- 15:00 Dentist",
  "pending_approvals": []
}
```

**b) Paused, waiting for the user to approve something**
```json
{
  "thread_id": "f79cdb0c-72fb-49c4-acbc-ad818bb8eb40",
  "reply": null,
  "pending_approvals": [
    {
      "tool": "create_calendar_event",
      "args": {
        "summary": "Dentist",
        "start": "2026-11-23T15:00",
        "end": "2026-11-23T15:30",
        "description": null,
        "location": null,
        "attendees": null
      },
      "description": "Tool execution requires approval\n\nTool: create_calendar_event\nArgs: {...}"
    }
  ]
}
```

| Field | Type | Description |
|---|---|---|
| `thread_id` | `string` | Conversation ID. **Always store it**: it's either the one you sent or a newly created UUID |
| `reply` | `string \| null` | The assistant's answer. `null` when paused for approval |
| `pending_approvals` | `PendingAction[]` | Empty when there's a reply. When non-empty, show approval UI and call [`POST /chat/approve`](#71-post-chatapprove) |

**How to tell them apart:** `pending_approvals.length > 0` means the assistant paused. Otherwise, render `reply`.

**About `reply` text:**
- It's plain text that **may contain Markdown**: lists, `**bold**` and links. Render it with a Markdown renderer that sanitises HTML.
- It may contain links to Google Calendar events and Drive files.
- In rare cases it can be an empty string `""`.

**Errors**

| Code | `detail` | What to do |
|---|---|---|
| `409` | `"This conversation is waiting for your approval. Use POST /chat/approve first."` | The thread has pending approvals. Show them, and disable the message input until they're resolved |
| `422` | validation array | Bug in the request body |
| `500` | plain text | Usually OpenAI or Google trouble. Show "Something went wrong, try again" |

**Timing:**
- A request takes **2–60 seconds**, because the assistant may call several Google tools before answering.
- Show a loading or "thinking…" state.
- Don't use a short client timeout. **There is no streaming.**

### 6.2 Conversations (`thread_id`)

| Action | What to send |
|---|---|
| New chat | `thread_id` omitted or `null` |
| Continue chat | `thread_id` from the last response |
| Switch between chats (client-side list) | That chat's stored `thread_id` |

- The backend **does not list conversations or return message history.** The frontend must keep its own copy of the messages it displays, for example in `localStorage`.
- Conversations live **in server memory**. After a server restart, every `thread_id` is forgotten: sending an old `thread_id` simply starts a fresh, empty conversation, with no error.
- Any string is accepted as a `thread_id`. An unknown ID just starts a new conversation under that ID.
- **Send one message at a time per thread.** Wait for the response before sending the next one, and disable the input while waiting.

## 7. Approvals

Some actions change the user's data, so the assistant **pauses and asks first**. This is human-in-the-loop approval. It currently applies to:

| Tool | What it does |
|---|---|
| `create_calendar_event` | Creates a Google Calendar event, and **emails invitations** if there are attendees |
| `create_google_doc` | Creates a Google Doc |
| `create_drive_folder` | Creates a Drive folder |
| `rename_drive_file` | Renames a Drive file or folder |
| `move_drive_file` | Moves a Drive file or folder into another folder |
| `upload_file_to_drive` | Uploads a file from the server's local `uploads/` folder |

Read-only actions, like searching email or reading the calendar, never need approval.

### 7.1 `POST /chat/approve`

Sends the user's decision for **every** pending action in a thread.

**Request body**

```json
{
  "thread_id": "f79cdb0c-72fb-49c4-acbc-ad818bb8eb40",
  "decisions": [
    { "type": "approve" }
  ]
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `thread_id` | `string` | ✅ | The paused conversation |
| `decisions` | `Decision[]` | ✅ | **Exactly one decision per pending action, in the same order** as `pending_approvals` |

**`Decision` object**

| Field | Type | Required | Description |
|---|---|---|---|
| `type` | `"approve" \| "reject" \| "edit"` | ✅ | The user's choice |
| `message` | `string \| null` | ❌ | `reject` only: the reason, which is passed to the assistant, e.g. `"Make it 4pm instead"`. Default: `"The user rejected this action."` |
| `args` | `object \| null` | `edit` only: ✅ | The **complete** corrected arguments. Replaces the original `args` entirely, so include every field, not just the changed one |

**Examples**

Approve:
```json
{ "thread_id": "…", "decisions": [{ "type": "approve" }] }
```

Reject with a reason:
```json
{ "thread_id": "…", "decisions": [{ "type": "reject", "message": "Call it 'Dentist checkup' instead" }] }
```

Edit (the user changed the time in your form):
```json
{
  "thread_id": "…",
  "decisions": [{
    "type": "edit",
    "args": {
      "summary": "Dentist",
      "start": "2026-11-23T16:00",
      "end": "2026-11-23T16:30",
      "description": null,
      "location": null,
      "attendees": null
    }
  }]
}
```

Two pending actions (approve the first, reject the second):
```json
{
  "thread_id": "…",
  "decisions": [
    { "type": "approve" },
    { "type": "reject", "message": "Don't create the doc" }
  ]
}
```

**Response `200`**: the same `ChatResponse` shape as `/chat`:
- usually a `reply` confirming what happened, e.g. "Done, I created the event."
- **or a new set of `pending_approvals`.** The assistant can chain actions, for example creating a folder, then asking to move a file into it. Keep looping until `pending_approvals` is empty.

**Errors**

| Code | `detail` | Cause |
|---|---|---|
| `400` | `"Nothing is waiting for approval in this conversation."` | Already resolved, wrong `thread_id`, or the server restarted |
| `400` | `"Send N decision(s), one per pending action, in order."` | `decisions` length doesn't match |
| `400` | `"An 'edit' decision needs 'args' with the corrected arguments."` | `edit` without `args` |
| `422` | validation array | e.g. `type` not one of the 3 allowed values |
| `500` | plain text | Unexpected error |

**After a `reject`,** the assistant won't retry the same action. It usually replies asking what the user wants instead.

**When an approved action fails** (for example, Google rejects it), you still get `200`. The `reply` explains the problem, e.g. "I couldn't create the event: End time must be after start time."

### 7.2 `PendingAction` object

| Field | Type | Description |
|---|---|---|
| `tool` | `string` | Tool name. See [section 8](#8-approval-tool-reference) for each tool's `args` |
| `args` | `object` | The exact arguments the assistant wants to use. **Show these to the user** |
| `description` | `string` | Generic, developer-oriented text (`"Tool execution requires approval\n\nTool: …\nArgs: …"`). **Don't show it as-is**; build a friendly summary from `tool` and `args` instead |

## 8. Approval tool reference

Use this to render a friendly approval card for each `PendingAction`.

> **Optional arguments may be missing *or* `null`.** Treat `undefined` and `null` the same. When sending an `edit`, you may include optional fields as `null`.

### `create_calendar_event`

| Arg | Type | Required | Notes |
|---|---|---|---|
| `summary` | `string` | ✅ | Event title |
| `start` | `string` | ✅ | **Timed:** `"YYYY-MM-DDTHH:MM"` (local time in the user's Google Calendar time zone, e.g. `"2026-11-23T15:00"`). **All-day:** `"YYYY-MM-DD"` |
| `end` | `string \| null` | ❌ | Same format as `start`. **Timed:** if missing, the event lasts 1 hour. **All-day:** the **last day, inclusive**; if missing, it's a single day |
| `description` | `string \| null` | ❌ | Event notes |
| `location` | `string \| null` | ❌ | |
| `attendees` | `string[] \| null` | ❌ | Email addresses. ⚠️ **Google emails each one an invitation.** Make this obvious in the card |

How to tell the event type: `start.length === 10` means all-day; otherwise it's timed.
Suggested card: **📅 Create event** · "Dentist" · Mon 23 Nov, 15:00–15:30 · ⚠️ Invites: a@x.com

### `create_google_doc`

| Arg | Type | Required | Notes |
|---|---|---|---|
| `title` | `string` | ✅ | Doc name |
| `content` | `string` | ✅ | Plain-text body. Can be long, so show a collapsible preview |
| `folder_id` | `string \| null` | ❌ | Drive folder ID. `null` means the top level of My Drive. The ID isn't human-readable: show "in a folder" or the folder name if the assistant mentioned it |

Suggested card: **📄 Create Google Doc** · "Meeting notes" · preview of the first ~300 characters

### `create_drive_folder`

| Arg | Type | Required | Notes |
|---|---|---|---|
| `name` | `string` | ✅ | Folder name |
| `parent_folder_id` | `string \| null` | ❌ | `null` means the top level of My Drive |

### `rename_drive_file`

| Arg | Type | Required | Notes |
|---|---|---|---|
| `file_id` | `string` | ✅ | Drive file ID (not human-readable) |
| `new_name` | `string` | ✅ | |

Suggested card: **✏️ Rename file** → "new name"

### `move_drive_file`

| Arg | Type | Required | Notes |
|---|---|---|---|
| `file_id` | `string` | ✅ | File being moved |
| `destination_folder_id` | `string` | ✅ | Target folder |

### `upload_file_to_drive`

| Arg | Type | Required | Notes |
|---|---|---|---|
| `filename` | `string` | ✅ | A file name inside the **server's** `uploads/` folder. This is not an upload from the browser |
| `folder_id` | `string \| null` | ❌ | Destination folder, or `null` for the top level of My Drive |

> Drive IDs (`file_id`, `folder_id`, …) are opaque strings like `"1AbC…xyz"`. The names usually appear in the assistant's earlier messages. Showing the raw ID in a small, muted style is fine.

## 9. Direct data endpoints

These return Google data **without** going through the AI. They're quick (around 1–3 s) and cost nothing in OpenAI usage. They're useful for dashboard widgets like "Next events", "Recent emails" and "Recent files". Each one returns the **5 most recent items**; no query parameters are supported yet.

Common errors for all three:

| Code | `detail` | What to do |
|---|---|---|
| `401` | `"Google is not connected. Visit /auth/google."` | Show the Connect Google button |
| `502` | `"Google API error: <reason>"` | Google refused, e.g. an API is disabled. Show the message |
| `500` | plain text | Often a revoked login. Check `/auth/status` |

### 9.1 `GET /google/emails`

The 5 most recent Gmail messages, newest first.

**Response `200`**: `Email[]`
```json
[
  {
    "id": "19a4f2c3b1e0d9a8",
    "from": "Jane Doe <jane@example.com>",
    "subject": "Project update",
    "date": "Sat, 21 Nov 2026 18:42:10 +0100",
    "snippet": "Hi, just a quick update on where we are with…"
  }
]
```

| Field | Type | Notes |
|---|---|---|
| `id` | `string` | Gmail message ID |
| `from` | `string \| null` | Raw `From` header, e.g. `Name <email>` |
| `subject` | `string \| null` | `null` if the email has no subject |
| `date` | `string \| null` | Raw email `Date` header in RFC 2822 format. `new Date(date)` parses it in all modern browsers |
| `snippet` | `string \| null` | About 200-character preview. May contain HTML entities like `&#39;`, so decode them before display |

### 9.2 `GET /google/events`

The next 5 upcoming Google Calendar events, soonest first.

**Response `200`**: `CalendarEvent[]`
```json
[
  {
    "id": "abc123def456",
    "summary": "Dentist",
    "start": "2026-11-23T15:00:00+01:00",
    "end": "2026-11-23T15:30:00+01:00",
    "location": null,
    "attendees": [],
    "link": "https://www.google.com/calendar/event?eid=…"
  },
  {
    "id": "xyz789",
    "summary": "Holiday",
    "start": "2026-11-30",
    "end": "2026-12-03",
    "location": null,
    "attendees": [],
    "link": "https://www.google.com/calendar/event?eid=…"
  }
]
```

| Field | Type | Notes |
|---|---|---|
| `id` | `string` | |
| `summary` | `string` | `"(no title)"` if the event has no title |
| `start` | `string` | **Timed:** ISO 8601 with offset (`2026-11-23T15:00:00+01:00`). **All-day:** `YYYY-MM-DD` |
| `end` | `string` | Same format. ⚠️ **For all-day events, Google's `end` is exclusive**: the event above covers 30 Nov to **2 Dec**. Subtract one day for display |
| `location` | `string \| null` | |
| `attendees` | `string[]` | Email addresses; empty if none |
| `link` | `string \| null` | Opens the event in Google Calendar |

> Careful: `new Date("2026-11-30")` is parsed as **UTC midnight**, which can show the previous day in some time zones. Parse date-only strings as local dates.

### 9.3 `GET /google/files`

The 5 most recently modified Google Drive files, excluding trash.

**Response `200`**: `DriveFile[]`
```json
[
  {
    "id": "1AbCdEfGhIjKlMnOpQrStUvWxYz",
    "name": "Meeting notes",
    "mimeType": "application/vnd.google-apps.document",
    "modifiedTime": "2026-11-21T17:03:22.512Z",
    "webViewLink": "https://docs.google.com/document/d/1AbC…/edit",
    "parents": ["0AFolderIdXyz"]
  }
]
```

| Field | Type | Notes |
|---|---|---|
| `id` | `string` | |
| `name` | `string` | |
| `mimeType` | `string` | Common values: `application/vnd.google-apps.document` (Doc), `…spreadsheet` (Sheet), `…presentation` (Slides), `…folder` (folder), `application/pdf`, `image/png` … |
| `modifiedTime` | `string` | ISO 8601, UTC |
| `webViewLink` | `string` (may be missing) | Opens the file in Google Drive |
| `parents` | `string[]` (may be missing) | Folder IDs. Missing for some shared files |

## 10. Frontend state machine

```
                ┌───────────────┐
   app load ──▶ │ CHECK_GOOGLE  │── GET /auth/status
                └──────┬────────┘
       not connected / │ connected & !needs_reconnect
       needs_reconnect │
          ▼            ▼
 ┌────────────────┐  ┌────────┐  user sends message   ┌──────────┐
 │ CONNECT_GOOGLE │  │  IDLE  │ ────────────────────▶ │ THINKING │ POST /chat
 │ (open /auth/   │  └────────┘ ◀──────────────────── └────┬─────┘
 │  google, poll) │      ▲        reply received           │
 └────────────────┘      │                                 │ pending_approvals.length > 0
                         │                                 ▼
                         │                       ┌─────────────────────┐
                         │  reply received       │ AWAITING_APPROVAL   │
                         └───────────────────────│ (input disabled,    │
                                                 │  show cards)        │
                                                 └─────────┬───────────┘
                                                           │ user decides
                                                           ▼
                                                 POST /chat/approve
                                                 → reply           → IDLE
                                                 → more approvals  → AWAITING_APPROVAL
```

**Rules:**
- **Disable the message input** during `THINKING` and `AWAITING_APPROVAL`.
- In `AWAITING_APPROVAL`, collect a decision for **every** card before submitting. Send them in one `/chat/approve` call, in the original order.
- If `/chat/approve` returns `400 "Nothing is waiting…"`, clear the cards and return to `IDLE`.
- If `/chat` returns `409`, the thread is still waiting. Re-show the approval cards if you have them; otherwise tell the user to start a new chat.

**Helper: a safe fetch wrapper that handles all the error shapes**
```ts
export async function api<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`${API}${path}`, {
    ...init,
    headers: { "Content-Type": "application/json", ...(init?.headers ?? {}) },
  });
  if (res.ok) return res.json() as Promise<T>;

  let message = `Request failed (${res.status})`;
  const text = await res.text();
  try {
    const body = JSON.parse(text) as ApiError;
    message = typeof body.detail === "string"
      ? body.detail
      : body.detail.map((d) => d.msg).join(", ");
  } catch {
    if (text) message = text; // 500s are plain text
  }
  throw Object.assign(new Error(message), { status: res.status });
}
```

## 12. Behaviour and limitations

| Topic | Behaviour |
|---|---|
| **Users** | Single-user: the backend is connected to **one** Google account, the owner's. There is no login or user concept in the API |
| **Conversation storage** | In server memory only. A restart wipes all conversations and pending approvals. No error is raised; old `thread_id`s just start fresh |
| **History** | No endpoint returns past messages or a list of conversations. The frontend stores what it displays |
| **Streaming** | None. `/chat` returns once the assistant has finished |
| **Concurrency** | Send one request at a time per `thread_id` |
| **What the assistant can do** | **Gmail:** read and search (no sending). **Calendar:** read, and create events (no edit or delete). **Drive:** read, search, create Docs and folders, rename, move, upload from the server's `uploads/` folder (no delete) |
| **Time zone** | Calendar times in approval `args` are **local to the user's Google Calendar time zone** and have no offset, e.g. `"2026-11-23T15:00"`. Display them as-is; don't convert from UTC |
| **Browser file upload** | Not supported. `upload_file_to_drive` only uploads files already in the server's `uploads/` folder |
| **Rate limits** | None enforced by the API. OpenAI and Google limits still apply |
| **OAuth callback** | Returns JSON rather than redirecting back to the frontend (see [5.3](#53-get-authgooglecallback)) |
| **CORS** | Not enabled (see [section 2](#2-before-you-start-cors)) |

## Security notes

- **The API has no authentication.** Anyone who can reach the server can read the owner's email and calendar, and request changes to their Drive and Calendar. Run it on `localhost` only, unless authentication is added first.
- **Approvals happen on the client side of the API.** `/chat/approve` trusts whoever calls it. The approval UI protects against the *AI* doing something unexpected; it does not protect against other people with network access.
- Never log or store `reply` content or email data in third-party analytics. It contains the owner's private email and calendar data.
- Render `reply` text with a **sanitising** Markdown renderer. The assistant quotes email content, which could contain hostile HTML or links.
